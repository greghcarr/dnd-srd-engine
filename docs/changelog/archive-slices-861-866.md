**Feat (slice 866): over-capacity Speed cap (≤ 5 ft) — closes `over-capacity-speed-5`**
RAW (Carrying Capacity): "While dragging, lifting, or pushing weight in excess of the maximum weight you can carry, your Speed can be no more than 5 feet." Slice 865 gave `computeEncumbrance` a binary `overCapacity` flag but nothing consumed it. `getEffectiveSpeedForMode` (the chokepoint behind every speed alias) now applies the cap as its last step: when carried inventory weight exceeds the size×STR×15 carry max, every mode's effective Speed is clamped to ≤ 5 ft (`Math.min(uncapped, 5)`). RAW "your Speed" is general → walk and the non-walk modes are all capped; the cap only lowers (a 0-set Grappled/Restrained stays 0, a `set` override like Phantom Steed clamps down). `GetEffectiveSpeedInput` already carries `{ character, content, itemInstances }`, so no signature change; an empty inventory takes a no-weigh fast path. The Boots of Striding and Springing exemption is deferred (the item ships inert). New 8-test slice-866 (walk capped over/at/under the max; the empty-inventory fast path; `getEffectiveSpeeds.walk`; an over-capacity Ghost's fly 40 → 5; an under-capacity flyer keeps fly 40; the only-lowers invariant). No new export/condition/effect/content. `tsc` clean; `test:fast` (644 files, 4839 passed — exactly +1 file/+8 tests over 865, zero golden cascade) + doc audits green.

**Refactor (slice 865): 2024 Carrying Capacity model — size-scaled carry + binary over-capacity — closes `encumbrance-variant-2014` + `carry-capacity-size`**
RAW (SRD 5.2.1, Carrying Capacity) has NO 2014-style "encumbered"/"heavily encumbered" tiers: carry max = STR × 15 × size factor, drag/lift/push is double, and the *only* consequence of exceeding the carry max is "your Speed can be no more than 5 feet." Two audit rows collapse into one model fix. **`computeCarryingCapacity`** now scales the STR×15 base by size (Tiny ×0.5, Small/Medium ×1, Large ×2, Huge ×4, Gargantuan ×8, reading `sizeOverride ?? species.size`) and returns `{ capacity, pushDragLift, breakdown }` — Goliath Powerful Build still counts one size larger on top. **`computeEncumbrance`** drops the duplicated flat formula (now delegates to the single carry source) and the `EncumbranceLevel` tier type + `unencumbered`/`encumbered`/`heavily-encumbered` labels; its result is binary: `{ carriedWeight, carryCapacity, pushDragLiftCapacity, overCapacity }` where `overCapacity = carriedWeight > carryCapacity`. The Speed ≤ 5 consequence is the follow-up `over-capacity-speed-5` (slice 866). `EncumbranceLevel` removed from `src/index.ts` + the derive barrel (exports snapshot loses the one type — the only non-additive change; `EncumbranceResult` stays, reshaped). New 12-test slice-865 (size factors Tiny→Gargantuan; ×2 drag/lift/push; Powerful Build Medium→Large; the binary over/at/under-capacity flag with real musket weights). slice-582 + tabulated-math + character-sheet tests updated to the new shape; all stay green. `tsc` clean; `test:fast` (643 files, 4831 passed) + doc audits green.

**Feat (slice 864): `validateAttunement` — attunement preconditions — closes `attune-prereq-not-validated`**
The content-less `applyItemAttuned` reducer gates the 3-slot limit + double-attunement but can't see whether an item even requires attunement, nor its restriction. Attunement is consumer-committed (no `planAttune`), so — the `validateMulticlass` pattern — the engine ships `validateAttunement(character, instance, content)` → `{ issues, unverifiedCondition? }`. `issues` are the machine-checkable blockers (item doesn't require attunement / already attuned / 3-slot limit full); `attunementCondition` ("by a Dwarf", "by a Spellcaster") is free-form prose the engine can't verify, returned as `unverifiedCondition` for the consumer/DM to confirm. New 5-test slice-864 (unrestricted item attunable; restricted item surfaces its condition; non-attunement item / already-attuned / slot-full all rejected). Exported `validateAttunement` + `MAX_ATTUNED_ITEMS` + `AttunementValidation` (additive exports snapshot); documented in api-overview. No reducer/behavior change to existing surfaces. `tsc` clean; `test:fast` (642 files, 4819 passed) + doc audits green.

**Feat (slice 863): jump distances (`computeJumpDistances`) — closes `no-jump-distance`**
RAW Long/High jump formulas were unmodeled. New pure derive in `speed.ts`, exported: `computeJumpDistances({ character, content, itemInstances })` → `{ longJumpFeet, standingLongJumpFeet, highJumpFeet, standingHighJumpFeet }`. Long Jump = effective STR score; High Jump = `max(0, 3 + STR mod)`; each standing variant = ⌊half⌋. Reuses `GetEffectiveSpeedInput` and reads **effective** STR (effect-stack floor/increase + drain — the Graze/armor-speed score), so Gauntlets of Ogre Power lengthen the jump. RAW each foot of jump costs a foot of movement — a consumer/positional concern, so the engine reports distances only. New 3-test slice-863 (the four distances at STR 16 / 8; the High-Jump min-0 clamp at STR 3; the Gauntlets effective-STR read → STR 19 jumps). Exports snapshot gains `computeJumpDistances` + `JumpDistances` (additive); documented in api-overview. No behavior change to any existing surface. `tsc` clean; `test:fast` (641 files, 4814 passed) + doc audits green.

**Fix (slice 862): a creature must have at least 1 HP to start a Long Rest — closes `rest-no-min-1hp`**
RAW (Long Rest): "To start a Long Rest, you must have at least 1 Hit Point." `planLongRest` applied the rest's benefits to every participant unconditionally, so a 0-HP / dying creature could long-rest straight to full. A gate at the top of the planner now throws (naming the creature) if any participant is below 1 HP — it must regain ≥1 HP first (a heal, or the stable-creature 1-HP-after-1d4-hours recovery). Explicit failure over the prior silent rest-to-full; the gate lives in the planner (not the reducer the row cited) so the rejection surfaces before any event commits. New 3-test slice-862 (0-HP participant throws; ≥1-HP rests normally; a party rest with one 0-HP member is rejected, naming them). Every existing long-rest test stays green. No content/snapshot change. `tsc` clean; `test:fast` (640 files, 4811 passed) + doc audits green.

**Fix (slice 861): a creature that takes falling damage lands Prone — closes `falling-no-prone`**
RAW (Falling): "When the creature lands, it has the Prone condition unless it avoids taking any damage from the fall." `planFalling` applied the damage but never the Prone-on-landing. It now appends a `prone` ConditionApplied to the faller iff the fall dealt damage (the mitigated total > 0) — so Feather Fall (`GrantFallingProtection`), Slow Fall reducing to 0, and full Bludgeoning Immunity all leave the creature standing, while any fall that hurts knocks it Prone. The averaged-vs-rolled damage value (`falling-averaged-not-rolled`) is left unchanged (kept out to avoid the broad value-cascade a rolled-damage change pushes through every falling golden). New 2-test slice-861 (a damaging fall applies Prone after the DamageApplied; a Slow-Fall-to-0 fall returns `[]` with no Prone); the Slow Fall / Feather Fall / Death Ward unit tests stay green (they find events by type). Goldens regenerated: `s14-environmental` purely additive (a "is now Prone" line per fall); `showcase` a correct Prone-driven cascade (Vex attacks while Prone → Advantage cancelled, Sneak Attack drops → seeded-RNG cascade, replay-equivalent). No content/snapshot change. `tsc` clean; `test:fast` (639 files, 4808 passed) + doc audits green.
Detail: [slice-861.md](slice-861.md).
