**Engine (slice 407): plugin API - context enrichment + first planner retrofit (Elemental Weapon)**

This is the first of the three non-SRD planners to move out; Thunder Step + Absorb Elements remain (they need the save/damage context cluster, added when they're retrofitted). **Engine (slice 406): plugin API phase 1 - the custom-action seam**

First implementation step of the [plugin API design](../plugin-api-design.md): turn the previously-inert handler registry into a live extension point, so a content pack can ship consumer-supplied *code* (behavior) alongside its JSON instead of the engine hardcoding it. Motivated by the "the engine carries behavior for content it doesn't ship" concern (absorb-elements / thunder-step / elemental-weapon planners). This is the foundation those will eventually move onto.

`engine.plan.custom(state, { handlerId, params })` dispatches to a handler registered under `createEngine({ handlers: { action: { [id]: { plan } } } })`. New `ActionHandler` interface (`plan(ctx, params) -> Event[]`) for the action axis, alongside the existing `EffectHandler` (effect-lifecycle axis, still un-invoked, wired in a later phase). `HandlerContext` enriched from `{ state, rng }` to the minimal curated surface: `apiVersion`, `state`, `content`, `rng`, `at`, `rollDie`, `rollExpression`, `newEventId`, `newAppliedConditionId`; `HANDLER_API_VERSION = 1` lets plugin code guard against an incompatible host. Started with the action axis (B1) rather than effect-lifecycle (A) because it is both simpler to wire (one new plan method, no trigger/tick/expiry hooks) and the axis the retrofit-target spells actually use.

The seam honors the locked architecture's determinism contract: the handler runs at PLAN time, consumes `ctx.rng`, and bakes its rolls into the existing-typed events it returns, so `apply()`/replay never re-run it. New public exports: `ActionHandler`, `HANDLER_API_VERSION`.

Uncle Bob audit (engine slice): **Names** `ActionHandler` / `HandlerContext` / `HANDLER_API_VERSION` / `custom` say what they are. **DRY** the context is built once in `createEngine` and reuses the engine's existing `rng` / `content` / id minters; no parallel machinery. **SRP** the registry stores handlers, `engine.plan.custom` builds the context + dispatches, the handler owns the behavior. **Magic numbers** none (the API version is a named constant). **at-threading** `custom` resolves `at` once (`intent.at ?? nowIso()`) and threads it into the context for the handler to stamp on every event. **Mechanical outcomes asserted** the handler is invoked + bakes a 2d6 roll into a DamageApplied, the context exposes the API version, the committed events replay deterministically (no apply-time RNG), and an unregistered handlerId throws a clear error. **Tests** pin the seam end-to-end including replay-equivalence; planner-wiring audit allowlists `custom`; contract snapshot updated for the two new exports. No content change. No em/en dashes. `tsc --noEmit` clean; full suite green (333 files / 2173 passing).

**Docs (slice 405): plugin API design proposal**

Wrote [docs/plugin-api-design.md](../plugin-api-design.md), a design (not implementation) for letting a content pack ship consumer-supplied *code* (handlers for bespoke mechanics) alongside its JSON. Surfaced that the extension scaffold (`HandlerRegistry`, `EffectHandler` onApply/onTick/onExpire, `engine.handlers?`, `Custom { handlerId }`) exists but is **inert**: `opts.handlers` is never read, the `Custom` case in the effect-stack builder is a no-op, and handlerIds are only marker strings hardcoded planners key off. The doc pins the hard constraints the locked architecture imposes (plan/commit -> handlers run at plan time and bake RNG; pure `apply()` + replay -> handlers never run at apply/replay; events-only -> handlers emit existing event types, never new ones), defines the two extension axes (effect-lifecycle vs action/cast), a curated + versioned `HandlerContext` surface, the pack<->plugin wiring (`requiredHandlers` manifest + load-time validation), the security model (engine never auto-imports), and a 6-phase incremental plan. Open questions (Axis B shape, context breadth, and whether the maintenance cost is worth it now) left for decision before implementation. No code change.
