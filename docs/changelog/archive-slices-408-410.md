**Engine (slice 409): ContentBundle - a pack + its handlers as one unit (single-file user content)**

Lets a consumer author a content pack and the behavior it supplies in a single module, and feed it to the engine as one input. New `ContentBundle { pack: ContentPack; handlers?: HandlerRegistry }`; `createEngine` gains an optional `bundles?` (and `contentPacks` is now optional, since a consumer can supply everything via bundles). A bundle's `pack` joins the content packs, its `handlers` merge into the registry via the new `mergeHandlerRegistries`, which throws on a **handler-id collision across bundles** (mirroring the slice-400 pack id-collision policy, so two bundles can't silently clobber each other's behavior). `opts.handlers` still works and merges alongside bundle handlers.

This is the answer to "can user content be a single file?": handlers must be code (JSON can't carry behavior), so a single-file pack is a `.ts`/`.js` module exporting a `ContentBundle` (data as a portable JSON import or an inline object literal, plus the handlers). The bundle makes it one logical unit and one `createEngine` input without forcing the data out of JSON. Documented in [content-packs/README.md](../../content-packs/README.md) with a worked single-module example.

New public exports: `ContentBundle`, `mergeHandlerRegistries`. Backward-compatible: existing `createEngine({ contentPacks, handlers })` callers are unchanged.

Uncle Bob audit (engine slice): **Names** `ContentBundle` / `mergeHandlerRegistries` / `bundles` say what they are. **DRY** the bundle path reuses `resolveContent` (pack id-collision) + the new registry merge; `createEngine` composes them once. **SRP** `mergeHandlerRegistries` only merges + detects handler collisions; `resolveContent` only merges + detects pack collisions; `createEngine` composes. **Magic numbers** none. **Mechanical outcomes asserted** a bundle joins its pack + registers its handler, `opts.handlers` + bundle handlers both register, a cross-bundle handler-id collision throws, a cross-bundle entry-id collision still throws, and `mergeHandlerRegistries` merges distinct / throws on dup. **Tests** pin each path; the contract type + export snapshots updated for the new shape + symbols. No content change. No em/en dashes. `tsc --noEmit` clean; full suite green.

**Engine (slice 408): plugin API - retrofit Absorb Elements; Thunder Step stays as shared vocabulary**

Second content-specific retrofit, and a deliberate stop. Moved Absorb Elements (XGE/TCE, non-SRD) out of the engine: deleted `planAbsorbElements` + `engine.plan.absorbElements` + its intent/outcome types, reimplemented it as a consumer-supplied `ActionHandler` ([tests/fixtures/handlers/absorb-elements.ts](../../tests/fixtures/handlers/absorb-elements.ts)) invoked via `engine.plan.custom`. Enriched `HandlerContext` with the two reaction helpers it needs: `assertReactionAvailable(character, label)` and `consumeActionEconomy(character, kind)` (both wrapping the now-exported reaction-economy helpers in `reactive-spells.ts`). The 11-case test drives the handler through `engine.plan.custom`; since the seam returns `{ events }` (not the old `{ events, halvedAmount }`), the absorbed-half assertions now read it from the `AbsorbElementsCast` event (which already carried it). planner-wiring allowlist dropped the stale `absorbElements` entry.

**Thunder Step is intentionally NOT retrofitted.** Investigating it surfaced that, unlike Elemental Weapon and Absorb Elements (genuinely content-specific behavior), `planThunderStep` is thin glue over CORE movement vocabulary: `resolveDestination` (terrain / occupancy / map geometry) and `findCombatant`, shared with SRD Misty Step + Dimension Door, plus the save/damage AoE pipeline. Moving it would force exposing the movement internals as permanent public plugin API for one spell, which violates the design's "expose what a planner needs, not raw engine internals" principle. It stays as shared-vocabulary glue. So the honest end state is not "all 3 planners out" but "the content-specific behavior is consumer-supplied; thin glue over core capabilities (exercised by SRD spells too) stays" - which fully addresses the original concern (the engine no longer carries content-specific behavior for unshipped spells).

Uncle Bob audit (engine slice): **Names** `assertReactionAvailable` / `consumeActionEconomy` / `absorbElementsHandler` say what they are. **DRY** the context helpers wrap the existing (now-exported) `assertReactionAvailable` / `economyConsumedIfEncountered` rather than reimplementing; the handler is a faithful port. **SRP** engine provides the curated context, the handler owns the reaction's behavior. **Magic numbers** the slot-scaling + allowed types cite RAW (carried from the deleted planner). **at-threading** the handler stamps `ctx.at` on every event. **Mechanical outcomes asserted** the 11 ported cases (halving per type, the charged rider + upcast `riderDamageDice`, the next-hit damage flowing through attack, reaction-already-used throws, 0-damage edge) all green via `engine.plan.custom`. **Tests** full behavioral parity; no contract-snapshot change (the method + types weren't barrel-exported). No content change. No em/en dashes. `tsc --noEmit` clean; full suite green (333 files / 2173 passing).

**Docs (slice 410): reconcile the class-audit status (it was stale)**

Investigating the "classes not yet individually audited" caveat found it was simply out of date. Classes ARE audited: slice 153 verified all 12 class + 12 subclass names match SRD 5.2.1, and slice 377's srd-drift class-feature-table parser asserts per-class Proficiency Bonus + the presence/level-placement of every feature name against `references/srd-markdown/classes.md` on every CI run. The five PHB-2014-flavored features the slice-153 audit flagged are all resolved (renamed to SRD names or dropped; verified none remain in the pack). So `content-attribution.md`'s "Not yet individually audited / per-feature SRD verification has not been done" line was wrong. Moved Classes into its own "drift-audited" section stating what IS verified (names + placement, CI-guarded) and the one residual manual check (per-feature numeric values in body prose, e.g. Roving's "+10 feet", which the table parser can't read). The "Not yet individually audited" section is now empty and removed. No code/content change; doc accuracy only.
