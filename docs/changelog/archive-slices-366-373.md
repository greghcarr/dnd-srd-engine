**Content + audit: retain item descriptions + a permanent phantom-field audit (slice 373)**

Closes the cosmetic data-loss the slice-372 sweep flagged and promotes the sweep itself to a CI guard. `ItemBaseSchema` lacked a `description` field (only `ConsumableSchema` / `GearSchema` declared it), so weapon / armor / tool / magic items had their authored `description` silently stripped at parse - 52 of the pack's 135 item descriptions were being dropped. Fix: moved `description` to `ItemBaseSchema` so every item kind inherits it (and removed the now-redundant per-kind declarations); all 135 descriptions are retained.

**Guard:** new [tests/audit/phantom-fields.test.ts](../../tests/audit/phantom-fields.test.ts) generalizes the slices 370-372 per-schema `.strict()` guards into one comprehensive check. It deep-diffs the raw pack against its `ContentPackSchema`-parsed form across every content category (spells, conditions, items, monsters, classes, subclasses, species, backgrounds, feats) and fails on any field present in the raw entity but stripped after parsing - the exact signature of the four bugs fixed in 370-372. An `ALLOWED_STRIPS` allowlist (empty today) documents any intentional strip, with a companion accuracy check. The audit reads zero strips across the whole pack.

New audit aside, no engine behavior change. Uncle Bob audit: **Names** `collectStrippedPaths` / `ALLOWED_STRIPS` read as what they do. **DRY** `description` lives once on the base instead of three copies; the diff walker is one recursive function reused for both the strip check and the allowlist-accuracy check. **SRP** the audit only compares raw vs parsed; it doesn't interpret semantics. **Magic numbers** none. **Tests** the audit prevents the entire phantom-field class (a field authored on a schema that drops it) anywhere in the pack, not just the three spell schemas now `.strict()`. No em/en dashes. `tsc --noEmit` clean; full suite green.

**Bugfix: Ray of Frost / Shocking Grasp didn't scale with level (slice 372)**

Generalized the slice-370/371 phantom-field sweep to **all** content (a raw-vs-Zod-parsed deep diff over every category). It surfaced a misplaced **top-level** `cantripScalingDice` map (`{ "5": "2d8", "11": "3d8", "17": "4d8" }`) on four cantrips - the engine reads only the per-mechanic `cantripScalingDice` string, so `SpellSchema` stripped the top-level map. **Ray of Frost and Shocking Grasp had it only at the top level** (not in their attack mechanic), so they stayed 1d8 at every level instead of scaling +1d8 at L5/11/17.

Fix: added `cantripScalingDice: '1d8'` to the Ray of Frost + Shocking Grasp attack mechanics (RAW Cantrip Upgrade) and removed the dead top-level maps from all four. **Guard:** `SpellSchema` is now `.strict()`, so a misplaced top-level field fails to parse loudly. Two residual notes (documented in [docs/starter-pack-gaps.md](../../docs/starter-pack-gaps.md)): **Eldritch Blast** scales by adding beams (separate attack rolls), not dice, so its map was a wrong model - removed and left a documented deferral (needs a multi-beam spell-attack primitive); **`items.description` is stripped from 52 items** (cosmetic data-loss, no mechanics) - a follow-up should add `description` to the item-kind schemas that lack it.

New [tests/unit/engine/slice-372-cantrip-scaling.test.ts](../../tests/unit/engine/slice-372-cantrip-scaling.test.ts): Ray of Frost and Shocking Grasp each roll more than a single 1d8 (8) on a non-critical hit at level 5 but not at level 1 (proving the scaling, excluding crits which double dice), the scaling lives on the mechanic, and `SpellSchema` rejects a misplaced top-level `cantripScalingDice`. No spell count change.

Uncle Bob audit: **Names** the per-mechanic `cantripScalingDice` is the engine's one scaling field; the misplaced top-level map is gone. **DRY** the fix uses the existing cantrip-scaling path (same as Fire Bolt); no new mechanism. **SRP** one `.strict()` on `SpellSchema` + the content field move. **Magic numbers** the 1d8 is RAW-cited content. **Mechanical outcomes asserted** the level-5-exceeds-1d8 scaling (crit-excluded), the mechanic carrying the field, and the `.strict()` rejection. **Tests** prevent a regression to non-scaling cantrips and a future misplaced top-level field. No em/en dashes. `tsc --noEmit` clean; full suite green; SRD-drift + spell-coverage green.

**Bugfix: melee spell attacks were tagged ranged (slice 371)**

Closes the second half of the slice-370 phantom-field sweep. The five RAW melee spell attacks - Shocking Grasp, Spiritual Weapon, Chill Touch, Flame Blade, Vampiric Touch - carried `attackKind: 'melee'`, but `SpellAttackMechanicSchema` had no `attackKind` field, so Zod stripped it and cast-spell hardcoded `attackKind: 'ranged'` on the `AttackRolled` event. The `event.attackKind` predicate fact ([src/engine/triggers/dispatch.ts](../../src/engine/triggers/dispatch.ts)) was therefore `'ranged'` for them, so melee-gated riders wouldn't fire and the ranged-in-melee disadvantage could wrongly apply.

Fix: added `attackKind: z.enum(['melee', 'ranged']).default('ranged')` to `SpellAttackMechanicSchema` ([src/schemas/content/spell.ts](../../src/schemas/content/spell.ts)); cast-spell now stamps `mechanic.attackKind` instead of the hardcoded `'ranged'` (the comment there had explicitly deferred this until "the first melee spell attack ships" - but five already shipped, mistagged). The attack schema is now `.strict()`, so a future authored-but-unsupported field fails to parse loudly. Both spell-mechanic shapes that silently dropped phantom fields (save in 370, attack in 371) are now closed + guarded; the slice-370 starter-pack-gaps follow-up is struck.

New [tests/unit/engine/slice-371-spell-attackkind.test.ts](../../tests/unit/engine/slice-371-spell-attackkind.test.ts): a melee spell attack (Shocking Grasp) tags the `AttackRolled` as `melee`, a ranged one (Fire Bolt) as `ranged`, all five RAW melee spells resolve `melee`, and `SpellMechanicSchema` rejects a phantom attack field.

Uncle Bob audit: **Names** `attackKind` mirrors `WeaponDefinition.attackKind` / the `AttackRolled.attackKind` field. **DRY** reuses the existing melee/ranged enum + the `event.attackKind` fact the weapon-attack path already populates; no new mechanism. **SRP** the schema gains one field; cast-spell reads it instead of a literal. **Magic numbers** none; the default `'ranged'` is documented. **Mechanical outcomes asserted** the `AttackRolled.attackKind` for a melee vs ranged spell, the five melee resolutions, and the `.strict()` rejection. **Tests** prevent a regression to all-ranged tagging and a future phantom attack field. No em/en dashes. `tsc --noEmit` clean; full suite green; spell-coverage + SRD-drift green.

**Bugfix: three save spells dealt zero damage (phantom-field strip) + a `.strict()` guard (slice 370)**

Found by sweeping a new bug class: wired-spell mechanic semantics that the SRD-drift audit doesn't check (it validates spell metadata, not the `mechanicalEffects` shape). A raw-vs-Zod-resolved diff of every spell mechanic surfaced **phantom fields silently stripped at parse**. **Sacred Flame, Burning Hands, and Thunderwave** were authored with an `onFailure: { damageDice }` + `onSuccess: 'half'` shape that `SpellSaveMechanicSchema` does not have, so Zod dropped both fields, leaving each as `{ kind: 'save', ability }` with no damage. cast-spell only reads top-level `damageDice`, so casting them emitted a `SaveRolled` but **no `DamageApplied`** - the three spells dealt zero damage at runtime. Two guards missed it: SRD-drift reads the raw authored `onFailure.damageDice` (which matched SRD) and the coverage test's `save` expectation only requires a `SaveRolled`.

Fix: converted the three to the supported `damageDice` / `damageType` / `halfOnSuccess` shape; Thunderwave's RAW 10-ft push now uses the supported `pushedFeetOnFail` (so it emits `CreaturePushed`), and Sacred Flame gained `cantripScalingDice: '1d8'` for its tier scaling. **Guard:** `SpellSaveMechanicSchema` is now `.strict()`, so an authored field the engine doesn't support fails to parse loudly instead of being dropped. New [tests/unit/engine/slice-370-save-onfailure-shape.test.ts](../../tests/unit/engine/slice-370-save-onfailure-shape.test.ts): the three now emit `DamageApplied`, Thunderwave emits `CreaturePushed`, the resolved mechanics carry top-level damage, and `SpellMechanicSchema` rejects the phantom `onFailure`/`onSuccess` shape. No spell count change (the three were already counted as wired, just broken).

The same sweep also flagged `attack.attackKind` stripped from 16 attack spells (cast-spell hardcodes `attackKind: 'ranged'`, so the 5 melee spell attacks - Shocking Grasp, Vampiric Touch, etc. - are tagged ranged). That is a separate, subtler fix (add `attackKind` to `SpellAttackMechanicSchema` + have cast-spell read it + `.strict()` the attack schema); tracked for a follow-up slice and noted in [docs/starter-pack-gaps.md](../../docs/starter-pack-gaps.md).

Uncle Bob audit: **Names** the supported `damageDice` / `halfOnSuccess` / `pushedFeetOnFail` fields read as the rulebook. **DRY** the three now use the same save shape as Fireball / Shatter; no new mechanic. **SRP** the schema change is one `.strict()`; the content change is the field rename. **Magic numbers** the dice + push distance are RAW-cited content. **Mechanical outcomes asserted** `DamageApplied` on cast for all three, the Thunderwave push, top-level damage on the resolved mechanic, and the `.strict()` rejection. **Tests** prevent a regression to zero-damage and a future phantom field being silently dropped. No em/en dashes. `tsc --noEmit` clean; full suite green; SRD-drift + spell-coverage green.

**Bugfix: Resistance cantrip 1d4 reduction is now wired (slice 369)**

Closes the last open empty-effect-condition bug from the slice-361 sweep, and the only RAW-drift among them. The `resisted` condition (Resistance cantrip) had no consume path, so the cantrip did nothing, and its description was the 2014-era "add 1d4 to a saving throw." SRD 5.2.1 Resistance is: choose a damage type at cast; when the creature takes that damage type, reduce the total by 1d4, once per turn, for the duration. Fix: new `planConsumeResistance` + `engine.plan.consumeResistance` ([src/engine/plan/reactive-spells.ts](../../src/engine/plan/reactive-spells.ts)), mirroring Absorb Elements exactly. Because the triggering `DamageApplied` has already committed (event-sourcing), the planner rolls the 1d4 and emits a compensating `Healed` for `min(1d4, damageAmount)`, so the creature's HP nets out at the reduced damage. The reaction costs no action and does not end the spell (Resistance persists).

The chosen damage type is consumer-supplied on the intent (validated against the eleven RAW Resistance types - Force and Psychic excluded), exactly as Absorb Elements takes its triggering `damageType`; the once-per-turn cap and the cast-chosen-type match are consumer-coordinated, documented on the condition. The `resisted` condition stays a single effect-less marker (no per-type fan-out needed, since the reaction is consumer-invoked - the same precedent Absorb Elements set), recategorized in pack-integrity's `EFFECT_LESS_OK` from a known-open bug to a consumer-invoked reaction marker. **The slice-361 known-open-bugs group is now empty** (all four closed across slices 366-369).

`consumeResistance` is wired like `consumeGuidance` (plan/index.ts export, engine/index.ts interface + impl, the `ConsumeResistanceIntent` / `ConsumeResistanceOutcome` barrel re-exports) and added to the planner-wiring audit's `EXCLUDED_FROM_DISPATCH` (a reaction, not a performIntent player action). The exports contract snapshot picked up the two new barrel types. No condition count change. New [tests/unit/engine/slice-369-resistance.test.ts](../../tests/unit/engine/slice-369-resistance.test.ts): the 1d4 roll + compensating `Healed`, the cap at the damage taken, and the guards (no Resistance active, a non-Resistance type, negative damage).

Uncle Bob audit: **Names** `planConsumeResistance` / `RESISTANCE_TYPES` / `reduction` read as the rulebook. **DRY** mirrors `planConsumeGuidance` (consumer-invoked, returns the rolled die) + Absorb Elements' compensating-`Healed` offset; reuses `rollDie` + the `Healed` event. **SRP** the planner validates + rolls + emits one compensating heal. **Magic numbers** `RESISTANCE_DIE_SIDES = 4` named; the eleven types are a RAW-cited constant. **at-threading** single `nowIso()`; the one d4 is the only RNG, in the planner. **Mechanical outcomes asserted** the 1d4 range, the compensating heal amount + cap, and the three guards. **Tests** prevent the do-nothing cantrip regression and a reduction exceeding the damage taken. No em/en dashes. `tsc --noEmit` clean; full suite green; planner-wiring + pack-integrity + exports-contract green.

**Bugfix: Bestow Curse "inactive turn" arm is now forced Dodge (slice 368)**

Closes the last empty-effect-condition bug from the slice-361 sweep (the note misread the RAW as random incapacitation). SRD 5.2.1 Bestow Curse's inactive-turn arm is "a Wisdom saving throw at the start of each of its turns or be forced to take the Dodge action that turn." `cursed-inert-active` already carried `recurringSave { onFail: 'consumeAction' }` (modeling the 2014 "waste your action" wording), so it lost the action but not Dodge's defensive benefit. Fix: a new recurring `onFail: 'dodge'` ([src/schemas/content/condition.ts](../../src/schemas/content/condition.ts) + [src/engine/plan/recurring-save.ts](../../src/engine/plan/recurring-save.ts)) that, on a failed save, emits `ActionEconomyConsumed` (action) **and** applies the `dodged` condition, mirroring `planDodge` exactly (a plain `ConditionApplied`; expiry comes from `dodged`'s own `endsOn`). `cursed-inert-active` switched to it, so a failed save now both loses the action and grants Dodge (attackers have Disadvantage, DEX saves with Advantage). The curse persists regardless of the save; only Remove Curse / concentration drop ends it.

The condition stays effect-less (the recurring save is the mechanic), recategorized in pack-integrity's `EFFECT_LESS_OK` from a known-open bug to a recurring-save-driven marker; the slice-361 open-bug list is now down to one (`resisted`, the Resistance-cantrip 2024 RAW-drift). No condition count change. The existing recurring-save test still passes (`'dodge'` also consumes the action); new [tests/unit/engine/slice-368-bestow-curse-inert-dodge.test.ts](../../tests/unit/engine/slice-368-bestow-curse-inert-dodge.test.ts) asserts a failed save emits both the `ActionEconomyConsumed` and the `dodged` `ConditionApplied`, both caused by the save.

Uncle Bob audit: **Names** the `'dodge'` onFail option reads as the rulebook action. **DRY** the new branch reuses the existing `consumeAction` action-consume + replicates `planDodge`'s `dodged` application (no new condition, no new expiry path - `dodged`'s `endsOn` handles it); both onFail kinds share the active-combatant gate. **SRP** the recurring-save planner still does one thing (roll the save, apply the onFail/onSuccess outcome). **Magic numbers** none. **Mechanical outcomes asserted** action consumed + `dodged` applied on failure, both caused by the save. **Tests** prevent a regression to action-loss-without-Dodge and the existing consumeAction path. No em/en dashes. `tsc --noEmit` clean; full suite green; pack-integrity green.

The single `cursed-ability-active` is removed; `cursed-attacks-active` / `cursed-inert-active` / `cursed-vulnerable-active` arms are unchanged. All six carry `category: 'curse'`, so Remove Curse strips them like any other curse.

Counts: conditions 121 -> 126 (rider 106 -> 111; 111 carry effects). Updated the conditions citations in status.md / getting-started.md / starter-pack-gaps.md (the slice-362 doc-counts audit enforces these) and the coverage snapshot (+6 conditions, -1). Removed `cursed-ability-active` from pack-integrity's `EFFECT_LESS_OK` (it no longer exists; the six replacements carry effects); two open empty-effect bugs remain (`resisted`, `cursed-inert-active`). No em/en dashes. `tsc --noEmit` clean; full suite green (314 files, 2092 passing); doc-counts + pack-integrity green.

**Bugfix: Hideous Laughter is now action-blocking (slice 366)**

Closes the first of the empty-effect-condition bugs the slice-361 sweep logged. Hideous Laughter applied `hideous-laughter-active` on a failed WIS save and the condition already carried a recurring end-of-turn save, but the id was **missing from `ACTION_BLOCKING_CONDITIONS`** ([src/engine/plan/_actor-state.ts](../../src/engine/plan/_actor-state.ts)) - so a creature "incapacitated by laughter" could still take actions. RAW 2024: on a failed save the target has the Prone and Incapacitated conditions. Incapacitated and Prone are engine-coded base conditions (Incapacitated via the action-blocking allowlist, Prone via the literal-id attack logic), so the fix mirrors the `held-paralyzed-active` (slice 339) / `power-word-stunned-active` precedent: add the variant id to the allowlist. The variant correctly stays effect-less (recategorized in pack-integrity's `EFFECT_LESS_OK` from a known-open bug to an action-blocking variant; the slice-363 accuracy check is satisfied because it remains empty-effect).

Documented RAW deviations (unchanged): the Prone attacker-side rule (melee attackers Advantage, ranged Disadvantage) is keyed off the literal `prone` id and is not reproduced by the variant id (the same limitation `held-paralyzed-active` carries for Paralyzed's attacker-side bonuses); the extra repeat save with Advantage on taking damage stays deferred (the recurring-save infra is turn-end only). New [tests/unit/engine/slice-366-hideous-laughter.test.ts](../../tests/unit/engine/slice-366-hideous-laughter.test.ts): the variant is registered action-blocking, and a creature that fails the save has `findActorBlockingCondition` return the id + `assertActorCanAct` throws. The starter-pack-gaps "Empty-effect condition gaps" log strikes Hideous Laughter (three open bugs remain: `resisted`, `cursed-ability-active`, `cursed-inert-active`).

Uncle Bob audit (bugfix slice): **Names** unchanged; the allowlist entry reads as the rulebook. **DRY** reuses the existing `ACTION_BLOCKING_CONDITIONS` id allowlist + the already-wired `recurringSave`; no new mechanism. **SRP** the fix is one allowlist membership + a description; the recurring save and concentration linkage were already correct. **Magic numbers** none. **Mechanical outcomes asserted** action-blocking membership + `assertActorCanAct` throwing for a laughing creature. **Tests** prevent the regression where a Hideous-Laughter target could act. No em/en dashes. `tsc --noEmit` clean; full suite green; no condition count change (the variant stays effect-less).
