**Engine (slice 413): character-sheet view model (read layer, part 2)**

Second piece of the consumer-facing read layer (after slice 411's content browse): the assembled stats a D&D-Beyond-style character sheet renders. New `buildCharacterSheet(input)` in `src/query/` returns a `CharacterSheet` that *extends* `computeDerivedCharacter`'s `DerivedCharacter` (level, PB, ability mods, HP, AC, saves, spell slots, languages) and adds the computed-stats that aggregate omits: all 18 `skills` (each with `ability`, `proficiency` level, total `modifier`, advantage/disadvantage), the three `passiveScores` (perception / investigation / insight), and `initiative` (DEX mod + `initiative`-target effect modifiers, with advantage). Pure assembly over existing derivations (`computeAbilityCheck`, `computePassiveScore`, the effect stack): it invents no rules, so RAW correctness lives in the derivations it composes. The effect stack is built once and threaded into the per-skill proficiency lookup rather than rebuilt 18 times.

Building this surfaced the slice-412 background-proficiency bug (skills showed wrong modifiers); that fix landed first, so the sheet sits on correct numbers.

New public exports: `buildCharacterSheet` + the `CharacterSheet` / `SkillView` / `PassiveScores` / `InitiativeView` types. Deferred to follow-up read-layer slices, each its own derivation cluster: the **attacks list** (needs weapon resolution from inventory), **spell save DC / attack bonus**, **effective speeds** (no derive helper exists yet), and the **inventory / equipment summary**.

Uncle Bob audit (engine slice): **Names** `buildCharacterSheet` / `SkillView` / `PassiveScores` / `InitiativeView` say what they hold; `skillView` names the per-skill assembler. **DRY** reuses `computeDerivedCharacter` for the base instead of recomputing it, and shares one effect stack across the skill-proficiency lookups. **SRP** `buildCharacterSheet` only assembles; each composed derivation still owns its rule. **Magic numbers** none (passive base 10 lives in `computePassiveScore`; proficiency tiers in the effect stack). **at-threading** n/a (pure reads). **Mechanical outcomes asserted** the sheet carries every `DerivedCharacter` field; lists 18 skills in canonical order each mapped to its ability; each skill's modifier equals ability mod + the proficiency contribution (covers both proficient and none branches); passive = 10 + matching skill modifier; initiative = DEX mod with no initiative effects; raising level raises a proficient skill's modifier by exactly the PB delta. **Tests** 6 cases over the fighter fixture, fixture-independent invariants. No content change. No em/en dashes. `tsc --noEmit` clean; full suite green; contract export snapshot updated.

**Engine (slice 412): fix background-granted skill/tool proficiencies never reaching ability checks**

Surfaced while building the character-sheet view model (slice 413): a soldier-background fighter's Athletics check returned just the STR modifier, not STR + proficiency bonus. Root cause: backgrounds carry their two skill + one tool proficiencies as structured arrays (`background.skillProficiencies` / `toolProficiencies`), but `buildEffectStack` only ingested `background.traits` (the effect list), so the structured arrays were read **nowhere** in `src/` outside the JSON itself. Every ability check, saving throw, and passive score silently dropped background proficiency. `computeAbilityCheck` reads proficiency solely from the effect stack, so this hit the core derivation, not just the sheet.

Fix: a `backgroundProficiencyEffects(background)` helper synthesizes `GrantProficiency` effects (`target: 'skill'|'tool'`, `level: 'proficient'`) from the structured arrays, ingested at both effect-stack assembly sites (`collectEffectsFromCharacter` + `buildEffectStack`) alongside `background.traits`. Skill choices granted by classes still flow through `PendingChoice` resolution as before; only the fixed background grants were missing. Pattern-checked the sibling shapes: species carry no skill/tool proficiency arrays (none to fix), and tool proficiencies rode the same gap (fixed in the same helper). The golden transcript shows the impact directly: Alyx's Athletics went from `+4` (failing DC 15) to `+6 (+4 STR-mod, +2 skill-prof(proficient))` (succeeding).

Uncle Bob audit (engine slice): **Names** `backgroundProficiencyEffects` says exactly what it builds. **DRY** one helper feeds both ingestion sites; no duplicated mapping. **SRP** the helper only maps arrays to `GrantProficiency` effects; the call sites only push them. **Magic numbers** none (`'proficient'` is the RAW grant level). **at-threading** n/a (derivation, no events). **Mechanical outcomes asserted** soldier Athletics = STR + PB; acolyte Religion (cleric) and sage Arcana (druid) now include PB while their non-granted siblings (Arcana / Nature) stay ability-mod-only; the no-proficiency path retargeted to a genuinely-unproficient skill. **Tests** the three derivation/engine tests that baked in the buggy values updated to the correct ones with explaining comments; golden transcript regenerated. No content change. No em/en dashes. `tsc --noEmit` clean; full suite green (336 files / 2199 passing).

**Engine (slice 411): content query/browse surface (read layer, part 1)**

First piece of the consumer-facing read layer, the surface a D&D-Beyond-style app renders. The engine is built to mutate state (plan -> commit events); a browser app is mostly reads ("all 3rd-level evocation spells a wizard can prepare", "CR 1-5 undead", "uncommon magic items"), and those had no surface. New `src/query/` module with three pure, deterministic filters over `ResolvedContent`: `querySpells` (level / level-range / school / class / concentration / ritual / name), `queryMonsters` (type / size / CR / CR-range / name), `queryItems` (itemKind / rarity / name). Per-category (not one polymorphic query) so each returns its category's precise type and mirrors DDB's separate browsers. Results come back in a stable display order (spells by level then name, monsters by CR then name, items by name) so a consumer renders them without re-sorting. Free-text `search` is a case-insensitive name substring; an exact `level`/`cr` overrides the range bounds.

New public exports: `querySpells` / `queryMonsters` / `queryItems` + their `SpellFilter` / `MonsterFilter` / `ItemFilter` types, and `MagicRarity` (the item-rarity enum type, now exported for filter typing). No state mutation, no new content, no engine-rule change.

Uncle Bob audit (engine slice): **Names** `querySpells` / `queryMonsters` / `queryItems` + `*Filter` say what they browse; `nameMatches` / `withinRange` / `itemRarity` / `compareByName` name the shared predicates. **DRY** the three queries share those four helpers rather than re-inlining substring / range / sort logic. **SRP** each query only filters + orders its one category; the helpers each do one comparison. **Magic numbers** none (filters carry no literals; the only ordering keys are the schema's own level/cr fields). **at-threading** n/a (no events emitted; pure reads). **Mechanical outcomes asserted** empty filter returns the full category in sorted order; exact level/cr overrides the range; range bounds inclusive (incl. fractional CR); school+class compose; class match case-insensitive; concentration/ritual flags; name substring case-insensitive; itemKind + rarity narrow correctly. **Tests** 14 cases run against the real SRD starter pack, so they double as production-content coverage. No em/en dashes. `tsc --noEmit` clean; full suite green; contract export snapshot updated for the new symbols.
