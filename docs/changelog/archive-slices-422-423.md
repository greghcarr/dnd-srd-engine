**Test (slice 423): ground-truth spell save DC / attack conformance**

Third 🟡→🟢 ledger upgrade. Spell save DC and attack are stated as formulas (not a table), so [tests/audit/srd-spell-dc-conformance.test.ts](../../tests/audit/srd-spell-dc-conformance.test.ts) parses two things from the SRD and recomputes: the **DC base constant** from `spells.md` (`"**Spell save DC** = 8 + ..."`) and **each caster class's spellcasting ability** from `classes.md` (`"_Spellcasting Ability._ <Ability> is your spellcasting ability for your <Class> spells"`). It then builds a caster with **distinct INT/WIS/CHA modifiers** and asserts `computeSpellSaveDC` / `computeSpellAttackBonus` equal `base + mod(SRD-ability) + PB` and `mod(SRD-ability) + PB`. The distinct mods are the teeth: if the engine picked the wrong spellcasting ability for a class (e.g. Ranger as INT instead of WIS), the DC would not match the value computed from the ability the SRD names. Covers all 8 SRD casters (Bard, Cleric, Druid, Paladin, Ranger, Sorcerer, Warlock, Wizard).

No engine/content change: every class already used its SRD-correct ability; the value is the non-circular verification. The `+ PB` structure is transcribed but quoted from `spells.md` in the test header. Skips when the SRD clone is absent. Ledger updated: spell save DC / attack is now 🟢; the scoreboard records AC (421) + weapon data/damage (422) + spell DC (423) as the upgraded set, with saves / skills / passives / speeds / finesse-ranged ability choice still 🟡.

Audit (test slice): no engine/content/public-surface change (no contract-snapshot diff). **Names** `srd-spell-dc-conformance` / `parseDcBase` / `parseClassAbilities` say what they do. **DRY** one parse of each SRD source feeds every per-class assertion. **SRP** the test parses + recomputes + compares; the DC rule stays in `computeSpellSaveDC`. **Magic numbers** the DC base (8) is parsed from the SRD, not transcribed; the distinct ability scores carry their intended mods in a comment. **Mechanical outcomes asserted** DC base = 8; ≥8 caster abilities parsed; per class, DC = base + SRD-ability mod + PB and attack = SRD-ability mod + PB. `tsc --noEmit` clean; full suite green (341 files / 2292 passing). **Test+content (slice 422): ground-truth weapon conformance — and it found real gaps**

Second 🟡→🟢 ledger upgrade, and the first to surface bugs. New [tests/audit/srd-weapon-conformance.test.ts](../../tests/audit/srd-weapon-conformance.test.ts) parses the **Weapons table out of `references/srd-markdown/equipment.md`** (weapon stats are *not* covered by srd-drift, so this was an unverified surface) and, per SRD weapon, asserts the pack's damage dice / type / versatile die / properties / mastery match the parsed cell, plus that `computeWeaponDamage` / `computeAttackBonus` produce the SRD die + STR mod + proficiency for a plain-melee wielder. Every expected value is parsed from the book.

It immediately caught **three real content defects** the author-asserted tests never would have: the pack was **missing Musket and Pistol** (both core 2024 SRD martial ranged weapons, 1d12 / 1d10 Piercing with Ammunition + Loading), and shipped **Light Crossbow under the stale 2014 name "Crossbow, light."** Closed all three in the same slice (the conformance test can't be green otherwise, and they're genuine SRD content): added Musket + Pistol to the starter pack and renamed the crossbow to its 2024 SRD name. Weapon count 52 → 54; the mastery-coverage snapshot gains the two firearms (Slow / Vex).

This is exactly the point of the ground-truth approach: parsing the book instead of trusting the author's recollection turned "looks complete" into "is complete," and the gaps were invisible to every prior test. Ledger updated: weapon data fidelity is now 🟢 (§2), and the plain-melee weapon damage line is 🟢 (§3); finesse/ranged ability choice stays 🟡.

Doc counts updated across getting-started.md / status.md / starter-pack-gaps.md (CI-guarded by doc-counts). No public-surface change (no contract-snapshot diff).
